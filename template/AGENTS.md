# 全局前端开发规范

本规范适用于所有前端项目。AI 在分析、设计、编码、联调、构建和交付前端代码时必须遵守。项目自身已有明确规范时，优先遵循项目规范；未明确约定的部分遵循本规范。

## 一、通用原则

- 修改前先阅读项目结构、技术栈、构建脚本、现有组件、样式体系、请求封装和相关业务代码。
- 优先复用项目已有的组件、工具函数、类型、状态管理、请求封装和命名方式。
- 修改范围必须与需求直接相关，不得擅自替换技术栈、引入重复依赖或重构无关代码。
- 不得覆盖、还原或删除用户已有的未提交修改。
- 设计稿、接口文档和现有代码存在冲突时，先指出冲突；不得自行猜测业务规则。

## 二、Figma 设计稿还原

提供 Figma 设计稿、链接、节点 ID 或设计标注时，必须以 Figma 为唯一视觉依据，严格还原，不得凭个人审美调整。

实现前必须检查目标页面的完整结构、组件、Variants、Auto Layout、响应式约束和各状态。必须准确还原：

- 页面尺寸、内容宽度、栅格、布局方向、对齐方式和间距；
- 字体、字号、字重、行高、颜色、背景、边框、圆角和阴影；
- 图片尺寸、比例、裁切方式、图标尺寸和对齐；
- 按钮、输入框、标签、弹窗等组件；
- Hover、Focus、Active、Disabled、Loading、Empty、Error 等设计中定义的状态；
- 设计稿提供的桌面端、平板端和移动端布局。

实现要求：

- 优先使用 Flexbox、Grid、正常文档流和响应式约束；除设计明确要求外，不得使用大量绝对定位模拟页面。
- 不得添加设计稿中不存在的卡片、渐变、阴影、装饰、说明文字或交互，也不得删除设计稿中的内容和状态。
- 不得只针对单一分辨率写死页面。长文本、空数据、大数字和窄屏下不得溢出、遮挡或重叠。
- 完成后必须在设计稿对应视口中实际运行并截图，与 Figma 逐项检查布局、字号、间距、颜色、资源裁切和状态；不能仅以“编译通过”作为完成标准。
- 无法访问 Figma、缺少资源或设计信息不足时，必须明确报告并请求补充，不得用猜测完成正式实现。

## 三、Figma 图片、SVG 和图标资源

- 图片、Logo、图标、插画和 SVG 必须优先从 Figma 原始设计文件导出或下载。
- 如果项目已接入组件库，且组件库中存在与 Figma 设计一致的图标，应优先使用组件库图标，不要重复下载或新增 SVG；组件库图标与设计稿不一致时，仍以 Figma 原始资源为准。
- 不得手工临摹 Figma 中已有的 SVG、Logo、图标或插画。
- 不得使用相似图标、Emoji、CSS 图形、Canvas、临时 SVG、占位图或随机网络图片替代正式资源。
- 不得为了使用图标库而新增重复依赖；除非项目已有对应依赖或设计稿明确指定，不得引入第三方图标库替代 Figma 资源。
- 不得把 Figma 临时预览地址作为生产资源地址；资源应放在项目约定的静态目录中。
- 保留资源原始宽高比和透明通道，SVG 导出后不得擅自修改 path 或图形内容。
- 引入资源前检查项目中是否已有相同文件，避免重复下载和存放。无法导出资源时必须说明缺失项，不得伪造。

## 四、组件、样式和代码质量

- 优先复用现有组件；只有存在真实复用需求或符合项目既有抽象模式时才新增公共组件。
- 页面专用逻辑放在业务模块内，避免过早全局抽象。组件职责应清晰，不得将请求、复杂转换、布局和多个独立交互无边界堆在一个组件中。
- 对复杂业务规则、关键判断、非直观实现和接口特殊约束等必要位置，必须补充简洁、准确、易懂的中文注释，重点说明实现原因和边界条件；不得添加逐行复述代码的无意义注释，代码变更后必须同步更新相关注释。
- 不得提交 `console.log`、`debugger`、临时 Alert、模拟数据或调试代码。
- TypeScript 项目不得用 `any`、大范围类型断言或双重断言绕过错误。接口参数和响应类型必须依据接口定义。
- 优先使用项目已有 CSS 方案和 Design Token。不得用全局样式污染无关页面，不得用 `!important` 掩盖层级问题。
- 语义正确地使用 `button`、`a`、`input` 等元素；图片、表单和交互控件必须满足基本可访问性。

## 五、接口联调

必须严格按照接口文档、接口类型和后端约定联调。

### 5.1 字段和数据结构

- 请求参数、响应字段、字段名称、层级、可选性、数据类型、枚举值、单位和时间格式必须以接口定义为准。
- 前端直接使用接口定义的字段，不得因为前端已有临时命名而进行无意义的二次重命名或转义。
- 不得同时维护一套“后端字段”和一套仅为改名而存在的“前端字段”。
- 不得猜测字段含义，不得把一个字段无依据地回退到另一个字段。
- 接口文档与实际响应不一致时，应指出并修正接口契约；不得静默兼容互相冲突的结构。

禁止以下无依据的字段兜底：

```ts
const name = response.name || response.userName || response.username || response.nickName;
```

如果接口定义字段为 `name`，直接使用 `response.name`。

### 5.2 禁止过度兜底

- 不得默认兼容多套未经定义的响应层级，例如同时尝试 `data`、`result`、`payload`、`body`。
- 不得用空数组、空对象、固定文本、模拟数据或可选链隐藏必填字段缺失。
- 不得通过 `try/catch` 吞掉接口异常后继续显示成功状态。
- 不得为未定义的异常结构编写大量兼容分支。
- 必填字段缺失时，应进入项目统一错误状态或暴露明确错误，便于修复接口问题。

以下是允许的必要处理：网络错误、超时、取消请求、HTTP 错误、登录失效、权限不足、接口明确声明的空状态、统一 Loading/Empty/Error 状态、防重复提交和必要的参数序列化。

只有在展示格式、图表/表格组件输入、表单提交结构、明确的 DTO/领域模型边界确实需要时，才允许做数据转换。转换必须集中、显式、可追踪，不得把简单字段读取包装成多层无意义映射。

## 六、构建、验证和产物清理

完成修改后，按项目实际脚本执行必要验证，例如：

```bash
npm run lint
npm run typecheck
npm run test
npm run build
```

使用 `pnpm`、`yarn` 或 `bun` 的项目必须沿用项目已有包管理器和锁文件。

- 不得忽略新增的编译、类型、Lint 或测试错误，不得通过关闭规则、跳过检查或删除测试绕过失败。
- 页面需求除构建验证外，必须实际在浏览器中检查；交互不能只通过阅读代码判断。
- 每次编译、打包或生产构建验证完成后，必须清理由本次操作生成且不需要交付的构建产物。
- 常见产物目录包括 `dist/`、`build/`、`out/`、`.next/`、`.nuxt/`、`.output/`、`coverage/` 和 `storybook-static/`，但必须先依据项目配置确认真实输出目录。
- 只能删除已确认的自动生成目录，不得删除源码、静态源资源、环境配置、用户文件或无法重新生成的文件。
- 不得删除项目原本已纳入版本控制的构建产物，除非任务明确要求。
- 清理前后都要检查 `git status` 和 `git diff`，确保没有误删、误改或遗留构建产物。
- 禁止对工作区根目录、用户目录或未确认路径执行递归删除命令。

## 七、交付检查

交付前必须确认：

- 页面已按 Figma 还原，并完成目标视口的实际视觉检查；
- 图片、SVG、Logo 和图标来自 Figma 或项目正式资源；
- 没有无依据的字段重命名、二次转义、模拟数据或过度兜底；
- 类型检查、Lint、测试和构建已按项目能力完成；
- 没有遗留调试代码、缓存、日志、临时截图和不需要提交的构建产物；
- 已检查工作区变更范围，并在交付说明中报告验证结果及仍存在的设计稿/接口问题。
